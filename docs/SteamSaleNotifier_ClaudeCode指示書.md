# Claude Code 引き継ぎ指示書

## 0. 事前準備

1. 空のディレクトリを作り、`git init` する
2. `SteamSaleNotifier_要件定義_v1.0.md` を `docs/requirements.md` として配置する
3. 下記「1. CLAUDE.md」の内容をリポジトリ直下に `CLAUDE.md` として置く
4. その状態で Claude Code を起動し、「2. キックオフプロンプト」を貼る

要件定義書を**リポジトリ内のファイルとして置く**のが重要です。チャットに貼り付けるとセッションをまたいだときに失われますが、ファイルなら Claude Code がいつでも読み直せます。

---

## 1. CLAUDE.md（リポジトリ直下に配置）

````markdown
# Steam Sale Notifier

Steam の所有ゲームのうちセール中のものを1日1回 Discord に通知するツール。
GitHub Actions 上で動作し、一般配布を前提とする。

## 仕様の正典
`docs/requirements.md` が唯一の仕様書。実装判断に迷ったら必ずこれを参照する。
要件定義と実装が食い違う場合、要件定義を優先し、変更が必要なら先に相談する。

## 技術スタック
- Python 3.12
- 依存は `requests` と `PyYAML` のみ（配布容易性のため追加禁止）
- 実行環境は GitHub Actions ubuntu-latest

## 絶対に守るルール
- Secrets（STEAM_API_KEY / STEAM_ID / DISCORD_WEBHOOK_URL）を
  標準出力・ログ・例外メッセージ・コミットに出力しない
- 外部 API を叩くコードにはリトライと待機を必ず入れる
- `state.json` は実行結果にかかわらず毎回 `last_run` を更新する
  （60日でワークフローが無効化されるのを防ぐキープアライブを兼ねる）
- ネットワークに繋がずにテストできるよう、API 応答はモック可能にする

## コーディング方針
- 型ヒントを付ける
- 例外は握りつぶさず、利用者が原因を特定できるメッセージにする
  （特に「所有ゲームが空で返る＝プライバシー設定 or キー不一致」は明示）
- 関数は単一責務。1関数40行を目安とする

## 作業の進め方
- フェーズ単位で作業し、各フェーズの完了時に一度止まって報告する
- 仕様が曖昧な箇所は推測で実装せず、質問する
- 各フェーズで必ずテストを書き、通ることを確認してから次に進む
````

## 2. キックオフプロンプト（最初に貼る）

````text
このリポジトリで Steam の所有ゲームのセール通知ツールを実装します。

まず `docs/requirements.md` と `CLAUDE.md` を読んでください。
読んだうえで、いきなり実装を始めず、以下を出力してください。

1. 要件定義の中で「曖昧」「矛盾している」「実装前に確認が必要」と
   判断した箇所のリスト（あなたの判断で潰さず、必ず質問として挙げること）
2. 実装フェーズの分割案（各フェーズの成果物と受け入れ基準を含む）
3. 特に技術的リスクが高いと考える箇所と、その検証方法

私が内容を確認して合意してから、フェーズ1に進みます。
````

**このプロンプトの意図**：性能の高いモデルほど、曖昧な仕様を「良さそうな解釈」で自動的に埋めて先に進んでしまいます。それ自体は優秀な挙動ですが、後から「そういう意図じゃなかった」と気づくと手戻りが大きい。最初に**曖昧さを明示的に洗い出させる**ステップを挟むことで、これを防ぎます。

## 3. フェーズ別プロンプト

合意したフェーズ分割に沿って、以下の順で進めるのが安全です。

### フェーズ1：土台と設定

````text
フェーズ1を実装してください。

- 要件定義 6章のファイル構成でディレクトリとファイルの骨組みを作る
- config.yaml の読み込み（config.py）
- 環境変数から Secrets を読む処理（未設定時は何が足りないか明示するエラー）
- ロガーの設定。Secrets を含む文字列を必ずマスクするフィルタを入れる
- .gitignore, requirements.txt, LICENSE(MIT)

受け入れ基準：
- 環境変数を未設定で実行すると、不足している変数名を列挙して終了する
- Secrets をログに出そうとしてもマスクされることをテストで確認できる
````

### フェーズ2：Steam API 層

````text
フェーズ2を実装してください。steam.py です。

最初に検証してほしいことがあります。
appdetails に filters=price_overview を付けたうえで appids にカンマ区切りで
複数の appid を渡した場合、全件の価格が返るかどうかを実際に確認してください。
確認用の使い捨てスクリプトを作って実行し、結果を報告してから実装方針を決めてください。

- 有効なら 50件ずつのバッチ取得
- 無効なら1件ずつ + config の request_interval_sec 待機

そのうえで実装するもの：
- get_owned_games(): 空レスポンス時にプライバシー設定/キー不一致を示す専用の例外
- get_prices(): 429 で指数バックオフ、success:false と price_overview 欠落はスキップ

受け入れ基準：
- ネットワークをモックしたテストが通る
- 検証結果に基づいてバッチ/逐次のどちらを採用したか、コメントで理由を残す
````

### フェーズ3：差分管理

````text
フェーズ3、state.py を実装してください。要件定義 FR-04 と FR-05 が該当します。

差分判定のロジックは、以下のケースを網羅したテストを先に書いてから実装してください。
- 新規セール開始 → 通知対象
- 割引率が上昇 → 通知対象
- 割引率が同じ → 通知しない
- セール終了 → 通知しない
- state.json が存在しない初回 → サマリーモード
- API 取得に失敗したゲーム → 既存エントリを消さない

受け入れ基準：
- 同じ入力で2回実行して2回目に通知が0件になる（冪等性）
````

### フェーズ4：Discord 通知

````text
フェーズ4、notifier.py を実装してください。要件定義 FR-06 です。

- 割引率降順ソート、embed 10件ごとにメッセージ分割
- max_notify を超えたら「他 N 件」を付記
- 初回サマリーモードの専用フォーマット
- エラー通知用の関数も用意する

実際に Discord に送らずに検証したいので、
生成されるペイロードを JSON として出力するドライランモードを付けてください。

受け入れ基準：
- 所有ゲーム80件がセール中という想定データで、
  ドライラン出力が Discord の制限（2000文字 / embed 10件）を超えない
````

### フェーズ5：GitHub Actions

````text
フェーズ5、.github/workflows/daily.yml を作ってください。要件定義 FR-07〜FR-09 です。

- schedule に timezone: 'Asia/Tokyo' を指定、cron は '17 10 * * *'
- workflow_dispatch を併記
- state.json の自動コミット（変更がなくても last_run 更新で毎日コミットされる）
- 毎月1日にワークフロー有効化 API を叩くステップ（continue-on-error: true）
- if: failure() で Discord にエラー投稿（実行ログへのリンクを含める）
- permissions は contents: write と actions: write

timezone フィールドは2026年3月以降の機能なので、
動作しなかった場合の UTC フォールバック手順をコメントで残してください。
````

### フェーズ6：README

````text
フェーズ6、README.md を書いてください。
要件定義 5章のセットアップ手順が該当します。スライドは作らず README に集約します。

重視してほしい点：
- 「つまずきポイント」として明記すべき箇所が要件定義に列挙してあるので必ず反映する
- 手順は番号付きで、1手順1アクション
- 最後に「Run workflow を押して Discord に届けば成功」で締める
- トラブルシューティング節を設ける（所有ゲームが0件、通知が来ない、60日問題）
- 免責事項（Valve非公式、Store APIは非公式エンドポイント）
- スクリーンショットを入れるべき箇所は <!-- SCREENSHOT: 説明 --> で場所だけ示す
````

## 4. 進行を安定させるコツ

**フェーズごとに必ずコミットさせる**
「フェーズNが完了したらコミットしてください」と都度伝えます。問題が起きたときに戻れる地点が増えます。

**「実装して」より「検証して報告して」**
フェーズ2の appdetails のように、外部仕様が不確かな箇所は、実装させる前に検証スクリプトを走らせて事実を確認させます。推測に基づいた実装が最大の手戻り要因です。

**受け入れ基準を毎回添える**
「何ができたら完了か」を先に示すと、実装が過剰にも過小にもなりません。上のテンプレートにはすべて入れてあります。

**要件を変えたくなったら、まず docs/requirements.md を更新する**
会話の中だけで仕様を変えると、セッションをまたいだときに元の仕様に戻ります。「要件定義書のこの節をこう変えてから実装して」と指示するのが確実です。

**セッションが長くなったら要約させて引き継ぐ**
「ここまでの決定事項と残作業を docs/progress.md にまとめて」と指示してから新しいセッションを始めると、文脈が途切れません。

## 5. 実装後の確認チェックリスト

- [ ] Secrets がログ・コミット・エラーメッセージに一切出ていない
- [ ] `state.json` が毎日コミットされる（セール変化がない日も）
- [ ] 同じ状態で2回実行して2回目の通知が0件
- [ ] 初回実行がサマリー形式になる
- [ ] `workflow_dispatch` が Actions タブに表示される
- [ ] わざと失敗させたとき Discord にエラーが届く
- [ ] LICENSE が MIT で著作権表示が入っている
- [ ] テンプレートリポジトリとして設定してある
- [ ] README だけを見て、自分でゼロからセットアップし直せる
